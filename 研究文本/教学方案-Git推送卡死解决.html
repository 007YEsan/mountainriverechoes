教学方案：GitHub 推送卡死的一次彻底解决

面向对象：民族学专业同学（零 git 基础）　|　总时长约 30–40 分钟　|　整理：肖娅琦

本方案用于把「git push 卡住不动」这个问题的解决过程，完整教给一位没有编程基础的同学。核心不是让他背命令，而是让他理解「git 为什么会去问一个组件要密码、那个组件为什么卡住、我们怎么把它换掉」这条链，从而以后自己也能排查。

一、教学目标

  • 能说清病症：知道 git push 卡死、超时的现象长什么样，并会和「网络不通」「密码错误」区分开。
  • 能说清原理：理解 credential.helper（凭证助手）是干什么的、为什么它「叠加」的特性会让 GCM 阴魂不散。
  • 能动手修好：会创建 GitHub 令牌（PAT）、会写凭证文件、会用「空值清空 + store」两行命令改配置。
  • 能自己验证：知道怎么判断「真的修好了」而不是假象。

二、课前准备（你这边）

  • 让同学准备好 GitHub 账号并能登录；确认他电脑已装 Git（有 git 命令即可，不要求装 Git Bash——用他手头任意终端都行）。
  • 确认同学的项目目录（比如 D:\musicdl）已经能 git push 到自己的 fork——只差授权这一步。
  • 你自己手机上准备好这份文档，方便随时翻。

三、教学流程（六步）

1先看现象，建立「同一个坑」的共识

约 3 分钟

让他回忆或复现：敲下 git push 后，光标一直闪、什么都不输出，等很久最后报超时。

关键提问，帮他把「病症」定位准：

  • 「网络能上 GitHub 吗？」——能。浏览器能打开 github.com，说明网是通的。
  • 「报的是密码错吗？」——不是。密码错会立刻返回 Authentication failed，不会卡。
  • 「那卡住说明什么？」——说明 git 在等一个东西回应，等不到。

2讲原理：git 的「要密码」是怎么走的

约 6 分钟

用一句大白话打底：git 自己不会存密码。每次要登录，它都去问一个叫「凭证助手」（credential helper）的小程序。

你电脑上有三个层级的配置，谁也逃不掉，按这个顺序被读：

层级文件这里放了什么
系统级PortableGit/etc/gitconfighelper-selector
全局~/.gitconfig指向 GCM（图形登录组件）
仓库级.git/config你改的那两行

卡住的就是 GCM——它本应弹出一个窗口让你登录 GitHub，但在某些 Windows 环境下，这个窗口弹不出来也退不出去，git 就一直干等。

3点破最难懂的一步：为什么「改了但还没生效」

约 6 分钟

这是整个问题的题眼，务必讲透：

credential.helper 是「叠加」的，不是「覆盖」的。

你写一句 git config credential.helper store，你以为把 GCM 换掉了——其实只是又在队尾加了一个。原来的 GCM 还在队里，git 挨个问过去，问到 GCM 照样卡死。

真正起作用的，是先写一句空值：credential.helper ""。空值的含义是「把前面注册的所有助手全部清空」。清空之后再挂 store，生效的才只有 store 一个。

可以打个比方：一队人排队接电话，你想让最后那个人接，就得先把前面所有人都请走，而不是再往队尾塞一个人。

4动手：三条命令改造凭证链

约 5 分钟

先说清楚：只要有 git 命令，用哪个终端都行——Git Bash、cmd、PowerShell、VS Code 的终端面板都可以，甚至让 AI 助手代你执行也行。Git Bash 不是必需的，它只是最省事的一个入口。要点只有两个：① 先 cd 进项目目录；② 下面的命令原样敲。

# 1. 加一个空值，清空前面所有已注册的助手（关键！）
git config --add credential.helper ""

# 2. 挂上 store：改用「读文件」的方式来拿密码
git config --add credential.helper store

# 3. 检查结果——应该看到「空行 + store」两行
git config --get-all credential.helper

注意第 1 条用的是 --add（追加一项），不是 git config credential.helper ""（那会被解析成「删除该项」）。这是第一个容易踩的坑。

为什么用 store？因为它最笨也最稳：不弹窗、不联网、不依赖任何图形组件——就是老老实实去读一个文本文件。

5动手：申请令牌，写进文件

约 8 分钟

第一步：生成令牌（Personal Access Token）。打开 https://github.com/settings/tokens/new：

页面上的项怎么填
Note（备注）随便，比如 本地备份
Expiration（有效期）选 90 days
Select scopes（权限）只勾最上面那个 repo

拉到底点 Generate token，页面顶部会出现一串 ghp_ 开头的字符——只显示这一次，点复制图标拿走。不要手动框选，容易漏字符。

长度自查：经典令牌一定是 ghp_ + 36 个字符 = 共 40 位。如果你拿到的明显更短（比如 24 位），那就是复制不全，回去重来。这个坑我踩过。

第二步：写进凭证文件。文件位置：C:\Users\你的用户名\.git-credentials（没有就新建）。内容一行：

https://你的GitHub用户名:刚才那串令牌@github.com

用记事本存成 UTF-8 无 BOM，别存成 .txt（文件名就叫 .git-credentials，注意开头有个点）。

安全提示：这个文件是明文存的，等于把钥匙写在纸上。所以令牌别设成永久（90 天够用），丢电脑了记得去 GitHub 撤掉令牌。

6验证：怎么知道真的修好了

约 6 分钟

这里有个大坑必须提前警告，否则他会以为成功其实是假象：

如果本地和远端内容完全一样，git push 会直接输出 Everything up-to-date 就结束——它根本不会联网、不会认证！所以看到这句话不能证明凭证有效。

要真验证，必须推一个「远端还不存在的东西」，比如一个临时分支。

推荐的三级验证（从轻到重）：

级别怎么做说明什么
① 只查身份curl -H "Authorization: token 你的令牌" https://api.github.com/user返回你的用户名 = 令牌有效
② 模拟推送git push --dry-run origin master不真的推，但走完整认证，能过就基本成了
③ 真实端到端建个临时分支推上去，再去 GitHub 网页确认看到它，然后删掉这才是铁证

四、教学检查点（确认他真的懂了）

  • 让他用自己的话解释：为什么单纯加 store 不够，非得先加空值？
  • 让他说出：Everything up-to-date 为什么不能用来证明修好了？
  • 让他独立完成一遍「生成令牌 → 写文件 → 验证」，你不插手。

五、常见追问与回答（备着用）

同学会问你怎么答
「为什么不修好 GCM，非要绕过它？」 GCM 那个卡死跟 Windows 环境、版本有关，修起来成本高还未必稳。用令牌是最直接、可复现的办法，效果一样好。
「令牌会不会被人看到？」 它在你自己电脑的文件里，明文存的。只要不外发、不截图给别人看就没问题。真要交作业截图，记得把令牌那行涂掉。
「90 天以后呢？」 令牌会过期，推送会开始失败。到时候重新生成一个、重新写进那个文件就行，其余配置都不用动。
「我电脑上也要开那个代理软件吗？」 访问 GitHub 需要的话就开着；这个跟我们改的凭证问题是两件独立的事，别混在一起排查。

六、给同学的一页速查卡（可直接发他）

我的 git push 卡住不动，怎么办？

  1. 先确认：浏览器能打开 github.com（说明网没问题）。
  2. 在项目目录里执行这两条： 
    git config --add credential.helper ""
git config --add credential.helper store
  3. 去 github.com/settings/tokens/new 建令牌：勾 repo，有效期 90 天，复制那串 ghp_（共 40 位）。
  4. 写进 C:\Users\你的用户名\.git-credentials： 
    https://用户名:令牌@github.com
  5. 验证：git push --dry-run origin master 不报错就算成了。

注意：看到 Everything up-to-date 不代表成功，那是没联网的空转。
